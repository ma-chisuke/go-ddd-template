# なぜこの境界なのか（在庫と受注の 2 つに割った理由）

> **この文書は事後の再構成です。** 実装が出来上がったあとに、現在のコードから逆算して境界の
> 根拠を言語化したものです。実プロジェクトでは**この検討を実装前に行います** — 境界を決めてから
> コードを書く、が DDD の順序です。ここでは「決め終わった結果」ではなく「どう決めたか」を
> 残すことで、あなたが自分のドメインで同じ判断をするときの手順として使えるようにしています。
>
> 決めた結果（コンテキスト間の関係と 3 つのフロー）は [context-map.md](./context-map.md) に、
> 語彙の対比は [glossary.md](./glossary.md) にあります。

## 1. 題材の業務フロー

このテンプレートの題材は、在庫を押さえてから注文を確定する、ごく小さな流れです。

1. 倉庫係が商品を**補充**する（`POST /stock/{sku}/replenish`）。
2. 顧客が**注文**を出す（`POST /orders`）。明細は SKU・数量・単価の並び。
3. 注文を受け付けるには、まず在庫を**予約**しなければならない。予約は仮予約（pending）で、
   期限（TTL）を持つ。
4. 予約が全明細ぶん取れたときに限り、注文を **Confirmed** として保存し、続けて予約を
   **確定**（confirmed）させる。取れなければ注文は成立しない。
5. 顧客が注文を**取り消す**と、押さえていた在庫を**解放**する。
6. 確定に至らなかった仮予約は、期限切れとして自動的に解放される（Reaper）。

登場人物は在庫と注文の 2 種類だけです。しかしこの短い流れの中に、**境界を引くべき理由が
3 つとも現れています**。

## 2. 語の衝突は境界の signal

同じ言葉を、話し手によって違う意味で使っている箇所があります。これが最初の signal です。

- 倉庫係の言う「**SKU**」は、棚にある在庫項目**そのもの**（同一性）です。
  注文係の言う「SKU」は、注文明細が**参照する**商品コードにすぎません。
- 倉庫係の言う「**数量**」は、足したり引いたりする在庫の数で、**0 も有効**です
  （「利用可能在庫 0」は正しい状態）。注文係の言う「数量」は注文行の個数で、
  **0 の明細は存在しません**。
- 倉庫係の言う「**予約参照**」は、外から渡ってくる不透明な相関 ID です。倉庫は「注文」という
  概念を持たないので、その由来を解釈しません。注文係にとって同じ語は、注文 ID から
  **決定的に導出する**値です（再試行しても同じ参照になる、という冪等性の土台）。

「1 つの語が 2 つの意味を持つ」とき、選択肢は 2 つしかありません — どちらかの意味に統一するか、
**語が別の意味を持つ場所に境界を引く**か。前者は必ずどちらかのドメイン規則を歪めます
（在庫の数量を 1 以上に狭めるか、注文行に数量 0 を許すか）。だから後者を選びました。

対比の詳細は [glossary.md](./glossary.md) にあります。この 3 語がそれぞれ独立した型として
`contexts/inventory/internal/domain/inventory/` と `contexts/ordering/internal/domain/order/` に
**別々に定義されている**ことが、境界が実在することの証拠です。

## 3. 境界線をどこに引いたか（3 つの基準）

### (i) 語の意味が変わる場所

上の 3 語がまさにそれです。言葉の意味が切り替わる面が、境界の第一候補になります。

### (ii) トランザクション境界（同時に一貫していなければならないものの単位）

- 在庫の**予約**は、在庫側だけで原子的に決まります。`available` は「有効な予約の合計」から
  導出されるため、予約の可否は在庫の状態だけを見れば判定でき、注文の状態を知る必要がありません。
- 注文の**確定・取消**は、注文側だけで原子的に決まります。取消できるのは Confirmed の注文だけ、
  という規則に在庫は関与しません。

2 つのトランザクションが独立に閉じるなら、それは別々の一貫性境界です。またがるやりとり
（予約の確定、取消による解放）は、同期呼び出しではなく**契約**（内部 API とメッセージ）で結びます。

### (iii) 変更理由の違い

在庫の引当規則（TTL の長さ、期限切れの扱い、マルチ SKU の全か無か）と、注文の規則
（価格の合計、取消できる状態）は、**別々の理由で・別々のタイミングで**変わります。
一緒に変わらないものを 1 つのモジュールに閉じ込めると、片方の変更が他方のテストを壊します。

## 4. 却下した代替案

### 案 A: 単一コンテキスト（1 つの `shop` に Order も StockItem も置く）

**却下**。上の 3 基準がすべて 1 つの集約境界の中に潰れます。とくに「同じ語が別の意味を持つ」という
最も教材価値の高い現象が消え、`SKU` も `Quantity` もどちらか一方の定義に統一せざるを得ません。
加えて注文の取消が在庫の解放と同一トランザクションになり、分散したときに必要になる設計
（腐敗防止層・アウトボックス・冪等な受信）を示す場所がなくなります。**小さい題材でも、示したい
構造は分けなければ現れない**、というのが却下の理由です。

### 案 B: 注文が在庫を内包する（Ordering が StockItem を子集約として持つ）

**却下**。在庫は注文以外の理由でも変わります（補充・棚卸し・期限切れの掃除）。注文集約の外から
変更されうるものを、注文の不変条件として守ることはできません。集約は「**同時に一貫していなければ
ならないもの**」の単位であり、在庫の可用数は注文の一貫性境界の外側にあります。無理に内包すると、
補充のたびに注文集約をロードするか、集約の不変条件が嘘になるかのどちらかになります。

### 案 C: さらに細かく割る（予約を独立したコンテキストにする）

**却下**。予約は在庫の可用数と**同一トランザクションで**決まります（`available` は有効な予約の
合計から導出されるので、予約を作ることと可用数が減ることは同じ 1 つの事実です）。切り離すと、
本来 1 つの原子的操作だったものに分散トランザクションが必要になります。**基準 (ii) を満たさない
分割はしない** — 境界は細かければよいというものではありません。

## 5. 引いた境界が機械的に守られていること

境界は文書で宣言するだけでは守れません。このリポジトリでは 3 段で強制しています。

1. **Go の `internal/` 規則（コンパイラ）** — 各コンテキストは 4 層を `internal/` に隠し、
   薄い公開ファサード（`contexts/<ctx>/<ctx>.go`）と公開 `port/` だけを見せます。
   兄弟モジュールが `internal/` を import するのはビルドエラーであり、lint の指摘ではありません。
2. **depguard（静的解析）** — [../.golangci.yml](../.golangci.yml) の
   `ordering-no-inventory-context` rule が、注文コンテキストから `contexts/inventory` への
   import を（テストも含めて）禁じます。同じ仕組みで `domain-purity`（ドメイン層の純粋性）と
   `shared-purity`（共有モジュールがコンテキストに依存しないこと）も守っています。
3. **到達手段そのものの制約** — 注文から在庫へは、在庫の内部 OpenAPI から生成したクライアント
   （`clients/inventory`）を通じて **HTTP 越しにのみ**到達します。腐敗防止層
   （`contexts/ordering/internal/adapter/outbound/aclhttp/`）が翻訳を担い、在庫の番兵エラーは
   注文側の番兵へ翻訳されて外へ漏れません。

3 つのフロー（同期予約 / 確定コマンド / 取消イベント）の詳細は
[context-map.md](./context-map.md) を参照してください。
